# 产品经理全流程 Agent 蓝图

> 本文档定义 PMAgents 系统的工作流设计:阶段划分、人机协作边界、Agent 能力清单、数据模型与门控机制。
> 代码实现与使用方式见根目录 [README.md](../README.md)。

## 1. 概述与设计原则

- **个人提效优先**:系统首先服务单个产品经理,减少重复劳动;团队协作作为扩展方向保留接口。
- **人机协作边界**:一切「起草、结构化、计算、汇总」类工作交给 Agent;一切**决策**(评审拍板、优先级确认、验收、资源承诺)与**真实世界信息采集**(研发状态、上线数据、用户反馈)必须人做。
- **产物落盘、断点续跑**:每步产物写文件,步骤间传文件路径而非大段文本;任何一步可单独重跑、可从中途续跑。
- **先跑通再扩展**:一期聚焦全流程闭环,工具集成(国产设计工具 API)分阶段验证后决定。

## 2. 端到端流程总览

```
 人 : 提供原材料 ────────────────────────── 评审拍板 ──── 资源假设 ── 录入过程/数据 ── 复盘决策
      │                                        │             │            │              │
Agent: 收集 → 分析 → 评估 → 设计 → 技术 → 原型 → 价值叙事 → [gate] → 排期 → ... → 复盘
      │      │      │      │      │      │       │           │      │          │
 产物: 需求池  卡片  优先级  PRD   可行性  原型规格 决策简报    评审结论 排期三件套  复盘报告
       清单          报告    初稿   报告   +HTML                           (表格/JSON/甘特)
```

评审点(人工 gate)位于「价值叙事」之后、「排期规划」之前:只有评审通过的需求才进入排期。

## 5. 数据模型与产物规范

- **需求卡片 JSON**(02_requirement_card.json):`user_role, scenario, pain_point, expectation, frequency, urgency, summary, completeness, missing_fields`
- **排期 JSON**(09_schedule_plan.json):`wbs_items[{id,name,module,depends_on,estimate_days,assignee_role,acceptance_criteria}], milestones[{name,date,items}], critical_path[], risks[]`
- **state.json**:`requirement_id, created_at, steps{<step>:{done,artifact,outputs,warnings,finished_at}}, warnings[]`
- **需求补充**(`input/supplement.md`):PM 追加的衍生信息(CLI `main.py supplement` 或面板主页面「输入预览」),多轮追加带时间戳、叠加不覆盖;**作为所有步骤的输入**;面板追加时选择当前所属步骤,保存后自动 force 重跑该步骤;CLI 追加后需对受影响步骤 `--force` 重跑才生效。
- **产物目录**:见 README「目录结构与产物规范」;每步产物序号=执行顺序,是断点续跑与 gate 的依据。

## 6. 评审与门控机制

- gate 定义:名称 + 对应文件 `gates/<name>_decision.md` 的【结论】行。
- 当前唯一 gate: `review`(需求评审),位于排期步骤之前。
- 结论取值:通过 / 有条件通过 / 打回。前两者放行,「打回」或「待填写」拦截。
- 打回后的流程:修改产物(如 PRD)并 `step <name> --force` 重跑 → 重新评审 → 更新 gate → `resume` 继续。
- 填写方式:人工编辑文件,或 CLI `main.py gate --set review --decision passed --note "..."`。
- **信息补充不是 gate**:需求补充是随时可用的旁路输入(不阻塞流水线);Web 面板在主页面「输入预览」中选择目标步骤追加,保存后自动 force 重跑该步骤;CLI 追加后由 PM 手动 `--force` 重跑相关步骤;`status` 与面板会提示补充是否晚于 analyze。

## 7. 原型工具落地路径

- **一期(已实现)**:Agent 直接产出原型规格文档 + 单文件 HTML 低保真原型,零外部依赖,浏览器打开即可评审演示。
- **二期**:以 HTML 原型/规格文档为输入,用国产工具自带 AI 能力转正式设计稿 + 人工精修(墨刀 AI / 即时设计 AI / MasterGo AI,能力实现前需验证)。
- **三期(条件性)**:对有开放平台/插件能力的工具做程序化导入;启动前验证:能代码创建画板与图层、能设定组件属性、有可用配额。
- 详细操作流程见 [prototype_tool_sop.md](prototype_tool_sop.md)。

## 8. 排期与复盘方法论

- **估时口径统一**:评估步骤的「实现成本」、技术步骤的「分模块人天」、排期的「任务估时」三处口径一致(1 人天 = 1 人 × 8 小时有效工作);排期总人天与可行性报告偏差 > 20% 须在风险项说明。
- **WBS 粒度**:0.5-3 人天/任务;必须覆盖 PRD 全部功能点;必须包含测试、联调、验收任务。
- **依赖管理**:每个任务标注 `depends_on`(任务 ID 列表);代码层校验依赖无环;关键路径显式输出。
- **复盘归因框架**:需求理解偏差 / 方案设计缺陷 / 技术实现问题 / 资源不足 / 外部依赖,归因须给出证据链(从过程记录/数据对比中引用)。
- **数据纪律**:复盘输入缺失时显式标注「未采集」,禁止编造或推断。

## 9. 扩展方向

1. **需求池跨需求复用**:收集步骤维护全局需求池(output/_requirement_pool/),供优先级评估做历史需求对比。
2. **国产工具程序化导入**:依三期验证结论决定是否实现(见第 7 节)。
3. **团队协作**:多人评审 gate、需求池共享、与项目管理工具(TAPD/Jira/飞书项目)同步研发状态。
4. **PRD 模板库**:沉淀历史 PRD 结构作为模板,提升方案设计一致性。
